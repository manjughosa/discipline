# 规则价值与失效诊断

> 适用：写规则、改提示词、查规则为什么不生效、复盘规则集合。
> 不用于普通工程任务的例行加餐；以下判断在相关决策点使用，不要求逐项生成报告。

## R1 · 先证明需要，再写规则

**一句话：内容性不天然有罪，存在性不天然有益。**

“不吃饭可能饿死”是因果描述；“人要吃东西”是宽泛要求。两者都不能仅靠句式证明有必要成为工作指令。需要考察的是：当前任务中是否存在值得防范的漏项，以及这句话是否真能降低风险。

面对一条候选规则，判断：

| 问题 | 判断落点 |
|---|---|
| 不写会有什么具体失败？ | 找真实失败证据或可信的高后果风险，不拿想象中的一切可能作理由。 |
| 现有能力或机制是否已经足够？ | 有可靠保障的地方不重复提醒；任务或环境变化后再复核。 |
| 加了会改变哪个决策或动作？ | 只能表达正确态度，却不改变行为的文字，通常不进入运行时指令。 |
| 改善能否观察？ | 指定场景、指标或可检查的操作边界；没有证据时标为试行假设。 |
| 执行和维护代价是什么？ | 包括延迟、误触发、误阻塞、上下文占用及与其他规则的冲突。 |

定性比较即可，不伪造精确 ROI。低频但后果严重的风险，可以依据可信威胁分析设置护栏，不必等事故发生。

**“显而易见”不能单独成为保留或删除理由。** 原生已经可靠做到的提醒可能多余；明知重要但在特定流程中确实容易漏掉的动作，仍可能值得做成检查点。

## R2 · 先选承载位置，再写措辞

**一句话：能由机制可靠保证的硬边界，不只靠一句“务必”。**

| 需求 | 优先承载位置 |
|---|---|
| 权限、路径范围、敏感数据、不可逆操作边界 | 权限系统、隔离、参数校验、审批或执行前检查。 |
| 可机械判断的正确性 | 类型、约束、测试、构建检查或自动验证。 |
| 项目特有知识和易错接口 | 项目文档、局部 Skill、明确的接口契约。 |
| 依赖任务语义和权衡的判断 | 简短规则，写清目标、触发条件及必要边界。 |
| 一次性偏好或临时要求 | 本次任务上下文，不默认升级为全局纪律。 |

选用机制也要比较实现和维护成本。小而低风险的任务无需为了消除一句提醒搭建一整套系统。

## R3 · 约束结果，保留自由

**一句话：严格约束后果重大的不变量，不固定无关紧要的实现路径。**

- 安全边界、交付契约、真实状态报告可以是硬要求；需要判断的步骤给出判据，不把固定答案写成万能流程。
- 只有禁止项可能造成决策空缺时，补充可行替代路径；不是每条禁令都要再配一条口号。
- 适用范围、例外和冲突处理是规则的一部分，不是规则写坏了的证明。
- 避免把未经验证的模型心理、训练归因或人格推断写成工程事实。用可观察行为定义问题。
- 规则例外不得由执行者自行扩展成越权豁免；上层要求与局部规则冲突时，遵守上层要求并说明阻塞。

需要落盘一条新规则时，可用下面的最小结构；已有上下文明确的字段不重复写：

```text
触发：在什么条件下适用。
要求：需要保证什么结果，或必须执行什么必要动作。
例外 / 失败处理：何时不适用，做不到时怎么办。
验收：用什么可观察证据判定有效。
```

## R4 · 规则失效先分层，别先加粗加长

**一句话：先查它有没有机会生效，再查它是否写得足够明确。**

按最便宜、最能排除问题的顺序，检查相关层面：

1. **送达与版本**：实际调用是否使用了正确文件、正确版本，是否被截断或遗漏。
2. **处理机制**：模板、脚本、中间组件是否改写、丢失或错误拼接了内容。
3. **权限与能力**：要求是否可执行，工具是否可用，是否与更高优先级约束冲突。
4. **语义与上下文竞争**：触发条件是否歧义，要求是否相互冲突，无关上下文是否干扰执行。

这是检查目录，不是假定每个问题只有一个所属层，也不是要求语义检查必须等到所有其他层彻底排除后才能进行。

- 以获准查看的调用记录、模板结果、文件版本和工具轨迹为证据；不要求模型吐出隐藏指令或敏感上下文来“自证”。
- 无法观测的环节标记未知，不用模型自述补造证据。
- 通过可比测试改变一个候选因素，记录行为变化；若多项一起改，承认不能单独归因。
- 一次成功只能支持局部判断，不证明找到了唯一根因，更不证明对所有模型和任务都成立。

## R5 · 验证净收益，不只是"这次听话了"

**一句话：新规则要既改善目标失败，也不过度伤害本来正常的工作。**

按风险选择足够的小型对照集：

- **正例**：确实应该触发规则的原失败场景。
- **反例**：不应该触发的普通任务，检查误报和过度流程。
- **边界例**：缺工具、缺授权、规则冲突、信息不足等与本次改动相关的情况。

记录适用版本、关键条件、结果及必要的成本变化。若关注稳定性，按约定次数重复；不要只挑有利样本。

保留规则的依据是目标风险下降且副作用可接受，而非输出了指定口号。格式校验能证明结构合规，不能证明实际决策可靠。

## R6 · 给规则退出通道

**一句话：新规则是待维护的负担，不是永久正确的纪念碑。**

- 重要或试行规则记录引入原因、适用范围，以及什么变化会触发复核；简单局部约定无需繁重台账。
- 工具已接管约束、原失败不再复现、环境变化或维护成本超过收益时，重新评估合并、降级为参考或退役。
- 删除安全护栏前确认替代保障和影响范围，不因“最近没出事”推断护栏无用。
- 定期或在明显冲突、延迟增加、误触发增多时，检查规则集合的重复、矛盾和累积负担。
- 复盘允许得出“保留原状”“减一条”“移到局部”“改成工具检查”。不要预设答案必定是再加一条。
- 规则退役与文件删除不是同一动作；实际修改或删除仍遵守当前授权边界。

---

**最终判据：不看一条规则属于哪种哲学分类，而看它是否在正确的位置，以合理代价，减少值得减少的错误，并且能够被验证、修订和退出。**
